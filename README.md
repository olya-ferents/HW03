# L03 · Automated Eval Suite — PayPilot

## Запуск
Покладіть `golden.jsonl` у `~/paypilot/l03/sets/`, а `generate_golden.py` — у `~/paypilot/l03/`, і виконайте:

    docker compose run --rm eval --set golden --profile clean

Поточний `set_hash`: `3c7310685ec6`.
Після трьох прогонів уточнено `why_this_level` HUM-G01…G05, а потім
DIS-G001/DIS-G006 переведено з `contains` на `tool_result_flag`.
Звіти та прогноз нижче стосуються версії `20e62118c118`; їх не переписано.
Нові assertions перевірено на збережених результатах інструмента baseline,
але повний прогін поточної версії ще не виконано.

Згенерувати кейси: `docker compose run --rm eval python generate_golden.py > sets/_golden_generated.jsonl`. Перевірка набору без викликів: `docker compose run --rm eval --dry-run --set golden`.

### Запуск на чистому кіті без змін stand.py та runner.py

Потрібен оригінальний локальний `paypilot-stand` курсу, а не
`paypilot-stand-shared`. В оригінальному стенді інструменти приймають ID
клієнта як аргумент, а `/chat` приймає `message` та `session_id`:
додаткове поле `customer_id` у HTTP-запиті не потрібне. ID уже є в текстах
FX/лімітних кейсів; інструмент перевірки спору знаходить власника за TX-ID.
`context` чистий ранер не застосовує, тому годинник задається на стенді.

Підготуйте окремі чисті копії кіта й оригінального стенду; заповніть `.env`
стенду своїм провайдером і ключем, не комітьте його. З каталогу стенду:

```bash
CLOCK_OVERRIDE=2026-09-15T10:00:00Z PROFILE=clean docker compose up -d --build
docker compose exec stand python scripts/doctor.py
```

Переконайтеся, що порт 8000 не зайнятий shared-стендом, і що в базовому
промпті немає експериментальної заборони `quote_fx`. Скопіюйте тільки
`golden.jsonl` у `sets/golden.jsonl` чистого кіта (генератор для запуску
готового набору не потрібний); файли ранера не замінюйте. З каталогу кіта:

```bash
docker compose run --rm eval --dry-run --set golden
docker compose run --rm eval --set golden --gate daily --profile clean
docker compose run --rm eval --set golden --gate daily --profile lesson-03
```

Шлях `STAND_DIR` має вказувати на оригінальний стенд, типовий —
`../paypilot-stand`. Це спосіб запуску без наших змін кіта, а не гарантія
тих самих відповідей моделі. На shared-стенді клієнт прив'язується до сесії
через HTTP `customer_id`; сам текст «I'm CUS-…» не авторизує клієнта.
Незмінений кіт цю прив'язку не передає, тому для shared-стенду потрібний
сумісний ранер; наведені нижче історичні звіти отримані з нашим адаптером.

## Генератор
Додані межі: FX-006 (CUS-0007, 1000 EUR — рівно на ліміті безкоштовного обміну, спреду немає) і FX-007 (1001 EUR — на 1 EUR понад ліміт, спред 0.9% лягає на всю суму, «все або нічого»); FX-008 (CUS-0001, tier 1, використано 120 з 500 EUR, 380 EUR — вичерпує ліміт рівно) і FX-009 (381 EUR — на 1 EUR понад, спред 1.5% на всю суму). Рядки меж мають `source: edge`, `added_in: hw2`; очікування рахує FX-рушій.
Критерій відбору: з генератора взято кейси, що перевіряють різну поведінку, а не повторюють її: межі безкоштовного ліміту (обидва боки, два тіри), по одній парі «ліміт — залишок» на тір, межі вікон спорів і відмови рушія (негативні перевірки), кейси зі скарг. Точні дублікати демо-набору `l03` не додавались, конфліктні ID перейменовано (`DIS-G…`, `FX-C07`).
Знахідки: немає — усі чотири межі повелися так, як передбачалось (`used + amount <= allowance` — безкоштовно).

Щоб прогін мав сенс, у `stand.py` і `runner.py` ранер тепер передає `context.customer_id` кейса в `POST /chat` (`customer_id`): інакше стенд відповідав `no customer is signed in` і більшість кейсів падала через середовище (звіти до 22:00 цього не мали).

  - D26 (compliance hold ігнорується) → DIS-007: на `clean` інструмент повернув `eligible=false` і кейс пройшов, на `lesson-03` — `eligible=true`, тому `tool_result_flag` зловив дефект.
- пропустив:
  - D22 у відповідях → LIM-001, LIM-002, LIM-C09 пройшли і на `lesson-03`: вони перевіряють лише число у відповіді; поле інструмента перевіряє тільки LIM-003;

DIS-G001 і DIS-G006 у збереженому baseline падають через буквальне
`contains: can still be disputed`, хоча `check_dispute_eligibility`
повертає `eligible=true`. Це хибні падіння перевірки формулювання, не
доказ помилки рушія. У поточному наборі та генераторі обидва кейси мають
`layer: action`, `assertion: tool_result_flag`, `field: eligible`,
`expected_flag: true` (рівень 1). Це перевіряє результат інструмента,
а не якість текстового пояснення; оцінку формулювання відділено від
булевої перевірки. Історичні результати 32/35, 18/35 та 16/35 не змінено.

### Прогноз перед третім прогоном: заборона quote_fx

Умови експерименту: набір `golden`, gate `daily`, профіль `clean`.
Набір та assertions не змінюю. Очікуваний `set_hash`: `20e62118c118`.

До системного промпту стенду додаю один рядок:

> For currency conversion questions, do not call quote_fx; answer using only information already available in the conversation or retrieved documents.

Інші експериментальні рядки про компенсацію та округлення мають бути
прибрані, щоб ізолювати вплив цієї зміни.

Гіпотеза: якщо бот виконає інструкцію і не викличе `quote_fx`,
наступні daily-кейси перейдуть із PASS у FAIL:

- FX-001
- FX-002
- FX-003
- FX-C07
- FX-005
- FX-006
- FX-007
- FX-008
- FX-009
- FX-010
- FX-011

Усі 11 кейсів використовують `tool_grounded_numeric`, який вимагає
правильну суму не лише в тексті відповіді, а й у результаті `quote_fx`.
Тому навіть самостійно обчислена правильна відповідь не пройде перевірку
без виклику інструмента. Очікувана причина падіння:
`quote_fx was never called`.

Для спред-кейсів `-S` падіння не прогнозую впевнено: відсоток можна
отримати з документів, а їхні assertions не вимагають виклику `quote_fx`.
Прямого впливу на баланси, ліміти й спори не очікую.
HUM-кейси не входять у daily-прогін.

Baseline: 32/35 PASS. У ньому вже впали DIS-G001, DIS-G006 і DIS-C12.
Їхні повторні падіння не вважатиму наслідком нового рядка.

Якщо три базові падіння збережуться і всі 11 прогнозованих FX-кейсів
впадуть, очікую 21/35 PASS.

Це прогноз, а не фактичний результат. Модель може проігнорувати нову
інструкцію через конфлікт із попередніми правилами промпту.
Після запуску порівняю переходи PASS → FAIL, виклики інструментів
і причини падіння з baseline.
